# 2. 해결하려는 문제

## 2.1 배포 실패 대응의 공백

배포 직후의 장애는 대부분 사람이 지표를 보고 판단한 뒤 수동으로 되돌립니다. 판단과 조치 사이에 지연이 생기고, 야간·주말에는 그 지연이 더 길어집니다.

자동 롤백을 하려면 "배포가 실패했다"는 판정과 "이전 상태로 되돌리는" 조치가 모두 자동화되어야 합니다. 그런데 금융·공공·통신의 운영 환경에는 다음 조건이 겹쳐 있는 경우가 많습니다.

- 베어메탈 서버, 프라이빗 클라우드 VM(OpenStack·vSphere·Nutanix·KVM), 컨테이너, 하드웨어·소프트웨어 로드밸런서가 한 서비스 안에 섞여 있습니다.
- 인터넷이 차단된 폐쇄망이라 SaaS 모니터링·APM 제품을 판정 근거로 쓰기 어렵습니다.
- 운영 환경을 도구가 스스로 바꾸는 것을 변경관리 절차가 쉽게 허용하지 않습니다.

Vigilante는 이 조건을 전제로 설계했습니다.

## 2.2 자동 롤백 자체의 위험

자동 롤백 도구는 운영 서버를 재시작하고, 로드밸런서에서 대상을 빼고, VM을 스냅샷으로 되돌립니다. 판정이 틀리거나 롤백이 실패하면 도구가 장애를 키울 수 있습니다. 그래서 Vigilante는 판정 보류(HOLD), 승인 모드, 서킷 브레이커, 장애 반경(blast radius) 제한, 반복 롤백 차단을 기본 구성 요소로 둡니다(docs/04-safety-circuit-breaker.md).

# 3. Vigilante가 하는 일

## 3.1 동작 흐름

Vigilante는 배포를 **스스로 측정하고, 규칙으로 판정하고, 실패하면 자동으로 되돌리는** 단일 Go 바이너리입니다. 외부 APM이나 별도 모니터링 스택 없이 동작합니다.

```
배포 ─▶ vigilante watch ─▶ 수집(HTTP/gRPC/TCP·/proc·docker.sock·로그·5xx·DB 풀)
                         ─▶ 판정(복합 규칙·베이스라인·연속 실패·대조군·관측 쿼럼)
                         ─▶ 롤백(드레인 → symlink/컨테이너/스냅샷 → 검증 → 복귀)
                         ─▶ 안전장치(서킷 브레이커·blast radius·플래핑·크래시 재개)
```

## 3.2 측정: 외부 APM 없이

Vigilante가 직접 대상에 접속해 지표를 모읍니다. 대상 호스트에는 SSH로 접속하며(에이전트 설치 불필요), 필요한 구간에만 선택형 경량 에이전트를 둘 수 있습니다(docs/01-architecture.md 1장).

| 프로브 | 수집 내용 |
|---|---|
| `http`·`grpc`·`tcp` | 응답 여부, 지연, 상태 코드, 연속 실패·타임아웃 |
| `host` | Linux `/proc` 기반 부하, CPU, 메모리, 디스크 I/O 사용률(busy %) |
| `docker` | 컨테이너 실행 여부, 재시작·OOM·종료 이벤트 (Podman 호환 소켓 포함) |
| `log` | 애플리케이션 로그의 패턴별 초당 발생 수 |
| `access_log` | 액세스 로그의 초당 요청 수, 5xx·4xx 비율, 요청 지연 |
| `db` | PostgreSQL·MySQL 쿼리 지연과 커넥션 풀 확보 가능 여부 |

로그 프로브는 원문을 저장하지 않고 수치 지표로만 바꿉니다(docs/02-config-spec.md "probes").

## 3.3 판정: 근거가 충분할 때만 롤백

- **복합 규칙:** 여러 지표를 조합한 규칙을 단계(canary·full 등)별로 평가합니다. 규칙은 위반·정상·판단 불가의 세 값으로 평가하며, 표본이 부족하면 통과시키지 않고 판단 불가로 처리합니다(docs/03-engine-design.md).
- **기준선과 연속 위반:** 배포 전 측정한 기준선과 비교하고, 위반이 정해진 횟수만큼 이어져야 실패로 봅니다.
- **환경 요인 구분:** 대조군(이전 버전 대상)도 같이 나빠지면 공용 의존성 장애로 보고 롤백하지 않습니다(HOLD).
- **관측 쿼럼:** 중앙 서버와 에이전트의 관측이 엇갈리면(네트워크 경로 문제 등) 롤백하지 않습니다(HOLD).
- **관측 장치 보호:** Vigilante 서버 자체가 과부하(CPU 부족, 소켓 고갈 등)이면 프로브 시간 초과가 대상 장애처럼 보입니다. `safety.observer_guard`(기본 켜짐)는 내부 타이머 지연, 루프백 왕복 시간, 여러 서비스에 걸친 시간 초과를 감시하다가, 그동안과 회복 후 1분 동안은 서버가 직접 재는 프로브(HTTP, TCP, gRPC, DB, SSH로 읽는 호스트)의 응답 여부·지연·연속 실패·시간 초과 지표와 프로브 오류(`probe_error`)에 근거한 위반을 롤백하지 않고 보류합니다(docs/04 S14a). 액세스 로그의 요청 지연처럼 대상이 보고한 값은 이 동안에도 그대로 판정합니다.
- **규칙 프리셋:** 내장 프리셋 4종(`java-web`, `container-api`, `static-web`, `worker`)으로 서비스 하나를 몇 줄로 설정할 수 있습니다. 단, 프리셋의 임계치는 아직 실제 서비스로 보정하지 않은 추정값이며 M8 파일럿에서 보정합니다.

## 3.4 롤백: 격리 후 복원, 확인 후 복귀

계획(`plan`)을 생략하면 기본 롤백 계획은 "트래픽에서 빼기 → 이전 버전으로 되돌리기 → 버전 사실 확인 → 트래픽 복귀"입니다(트래픽 제어기가 없으면 빼기·복귀 단계는 생략). 복귀 전 헬스 확인(`probe.verify`)은 계획에 직접 넣어야 하며, 권장 예시가 docs/02 "rollback"에 있습니다(internal/config/validate.go).

| 전략 | 방식 | 실행기·제어기 |
|---|---|---|
| A. 디렉토리 전환 | 릴리스 디렉토리의 symlink를 이전 릴리스로 원자적으로 교체하고 서비스 재시작 | `symlink` |
| B. 컨테이너 전환 | 이전 이미지로 컨테이너 재생성, 실패 시 원래 컨테이너 복구 | `container` |
| C. 트래픽 제어 | 로드밸런서에서 대상을 빼고(드레인) 복구 후 다시 넣기 | `nginx`, `haproxy`, `envoy`, `f5`, `aws_alb`, `octavia` |
| D. 스냅샷 복원 | 배포 전 VM·인스턴스 스냅샷으로 복원 | `vsphere`, `nutanix`, `kvm`, `openstack` |
| 범용 | 사내 스크립트 또는 사내 배포 시스템 호출 | `exec`, `webhook` |

- 1차 전략이 실패하면 지정한 다음 전략으로 넘어가며(에스컬레이션), 스냅샷 복원처럼 데이터 손실 위험이 있는 단계에는 사람 승인을 요구할 수 있습니다.
- 롤백이 끝까지 실패하면 대상을 트래픽에서 뺀 채 격리 상태로 두고 사람에게 넘깁니다.

## 3.5 안전장치

| 장치 | 동작 |
|---|---|
| 서킷 브레이커 | 일정 시간 안에 롤백 실패가 누적되면 자동 롤백과 새 배포 게이트를 모두 멈춤. 수동 차단(킬 스위치)도 가능 |
| 장애 반경 제한 | 드레인 후에도 풀의 최소 가용 대상 수가 유지될 때만 드레인. 아니면 한 대씩 제자리 롤백 |
| 반복 롤백 차단 | 시간당 롤백 횟수 상한과 대기 시간으로 롤백·재배포 반복을 막음 |
| 크래시 재개 | 모든 결정을 먼저 기록하고 실행. 재시작하거나 리더가 바뀌면 완료된 단계를 건너뛰고 이어서 수행 |
| 상태 저장소 장애 대응 | 쓰지 못한 기록은 메모리 대기열에 순서대로 쌓았다가 복구 후 기록. 장애 중 시작하는 롤백은 10초 동안 서비스 잠금을 다시 시도한 뒤 프로세스 안 잠금만으로 진행하고 그 사실을 이벤트·감사·알림으로 남김(`safety.rollback_lease`, `fail`로 바꾸면 롤백하지 않음) |
| 관측 장치 보호 | 서버 자체의 과부하 중에는 서버가 직접 재는 프로브의 실패 기반 위반을 보류(`safety.observer_guard`, 3.3절) |
| 드라이런 | 읽기·체크포인트만 실행하고 변경은 로그로만 남김 |

롤백 실패·비상 정지 시나리오 20종(S1~S18과 S12a·S14a)과 각 대응은 docs/04-safety-circuit-breaker.md에 정리되어 있습니다.

## 3.6 CI 파이프라인 연동

`vigilante watch`의 종료 코드로 파이프라인이 다음 단계를 결정합니다: 0 통과, 1 오류, 2 롤백 완료, 3 롤백 실패·서킷 OPEN·승인 대기·변경 동결·변경 티켓 게이트 거부, 4 보류(HOLD). `vigilante watch --server`로 판정을 서버에 맡겨도 같은 종료 코드를 쓰며, `--ticket`·`--freeze-override`도 서버로 전달됩니다. 이 종료 코드는 같은 MAJOR 버전 안에서 바꾸지 않습니다(docs/08-upgrade.md "호환성 약속").

# 4. 핵심 차별점

## 4.1 이기종 인프라를 하나의 흐름으로

베어메탈(symlink 배포), VM 스냅샷(vSphere·Nutanix·KVM·OpenStack), 컨테이너(Docker·Podman), 로드밸런서(Nginx·HAProxy·Envoy·F5·AWS ALB·OpenStack Octavia)를 같은 설정 형식과 같은 판정 엔진으로 다룹니다. 참조 설정(examples/config/vigilante.yaml)에는 베어메탈+F5, vSphere VM 위 Docker+HAProxy, EC2+ALB, OpenStack VM+Octavia의 네 서비스가 함께 들어 있습니다.

> **현재 한계:** 이 조합 대부분은 모의 서버·시뮬레이터로만 시험했습니다. 플러그인별 수준은 5장과 VGL-BD-03을 보십시오.

## 4.2 승인 모드: 자동 판정, 사람이 승인

서비스마다 `rollback.mode`를 `approve`로 두면, 실패 판정 시 롤백 계획(대상, 이유, 만료 시각)을 만들고 운영자의 승인을 기다립니다. 승인은 웹 콘솔·API·CLI로 할 수 있고, 기다리는 동안 문제 대상을 먼저 트래픽에서 뺄 수 있습니다(`drain_first`). 요청자와 승인자를 분리하는 4-eyes 옵션(`auth.four_eyes`, 웹 콘솔·API·로컬 CLI에 모두 적용)과 변경 동결 기간(`change_freeze`)도 지원합니다. 인증을 설정한 환경에서는 서버를 거치지 않는 로컬 CLI의 승인·거절, 서킷 리셋·차단, 동결 예외가 `--break-glass "사유"` 없이는 거부되며, break-glass 사용은 감사 기록과 critical 알림으로 남습니다(`auth.local_cli`).

로드맵은 운영 초기의 기본 운영 방식을 "자동 판정 + 사람 승인"으로 정하고, 파일럿에서 판정 품질이 확인된 서비스부터 완전 자동으로 전환하도록 권장합니다(docs/05 "설계 원칙" 6).

> **참고:** 하위 호환 때문에 `rollback.mode`를 적지 않으면 자동(`auto`)으로 동작하며, `vigilante validate`가 명시하라고 경고합니다.

## 4.3 폐쇄망 운영

- 웹 콘솔은 바이너리에 내장되어 있고 외부 CDN을 쓰지 않습니다.
- 바이너리·패키지·컨테이너 이미지·Helm 차트·SBOM·문서를 묶은 폐쇄망 설치 번들을 만들며, 서명 확인은 openssl만으로 할 수 있습니다(docs/07-install.md).
- 제품이 제조사로 사용 정보를 보내는 기능은 없습니다. 외부로 나가는 연결은 고객이 설정한 대상(대상 호스트, LB·하이퍼바이저 API, Vault, IdP, ServiceNow, 알림 채널)뿐입니다(docs/10-security.md "통신 경로").

## 4.4 단일 정적 바이너리

CGO 없이 빌드한 정적 바이너리 하나가 CLI, 서버, 에이전트를 모두 담당합니다. 런타임이나 별도 라이브러리 설치가 필요 없습니다. 필요한 플러그인만 쓰면 최소 빌드(vSphere·AWS ALB·gRPC 프로브·MySQL 드라이버 제외)로 바이너리 크기를 38MB에서 18MB로 줄일 수 있습니다(docs/05 M6 구현 결과).

## 4.5 감사 가능성

- 모든 판정·조치·권한 거부가 작업자(사용자, 서비스 계정, API 클라이언트, CLI 사용자@호스트), 출처, 사유, 변경 티켓 번호와 함께 기록됩니다.
- 기록은 해시 체인으로 연결되어 `vigilante audit verify`로 수정·삭제를 검출합니다. 체인 키(`audit.chain_key_ref`)를 설정하면 기록마다 HMAC이 붙어, 저장소에 쓸 수 있어도 키가 없는 사람은 기록을 고치고 체인을 다시 계산할 수 없습니다.
- syslog(RFC 5424 또는 CEF)로 SIEM에 실시간 전송할 수 있습니다. `tls://` 주소를 쓰면 RFC 5425 방식으로 수집기 인증서를 검증하며 암호화해 보냅니다.

세부 조건과 한계(체인 키를 쓰지 않을 때와 MAC 제거·키 교체 미지원 같은 보호 범위, 평문 `tcp`·`udp` 전송 선택 가능)는 VGL-BD-02 보안 점검표 응답서에 적었습니다.

## 4.6 롤백 경로의 독립성

웹 콘솔, ServiceNow, 알림, SIEM 같은 외부 연동이 장애여도 판정과 롤백은 계속 동작합니다. 외부 연동 실패는 기록이나 알림으로 처리하고 롤백을 막지 않습니다. 예외는 고객이 명시적으로 설정한 승인 게이트입니다(docs/05 "설계 원칙" 1). Vault 장애 시에는 캐시 시간(`secrets.cache_ttl`) 동안 이미 받은 비밀값을 계속 씁니다. ServiceNow 호출은 일시 오류(연결 오류, 429, 5xx)를 1·2·4초 간격으로 다시 시도하고, 인시던트는 백그라운드로 만듭니다. 상태 저장소(PostgreSQL·파일)가 끊겨도 롤백은 저장소를 기다리지 않습니다(3.5절 "상태 저장소 장애 대응", 한계는 6.2절).

# 5. 지원 플랫폼과 플러그인

## 5.1 검증 수준의 정의

| 수준 | 뜻 |
|---|---|
| **검증됨 (verified)** | 실제 시스템(장비·소프트웨어·클라우드)을 상대로 동작을 확인했고, 그 대상을 기록함 |
| **실험적 (experimental)** | 자동 테스트는 있지만 모의 서버·시뮬레이터 기준. 운영 사용 전 `vigilante doctor` 점검과 승인 모드 시작을 권장 |

같은 표가 바이너리에 들어 있어 `vigilante plugins`로 확인할 수 있고, `vigilante validate`와 서버 시작 로그가 사용 중인 실험적 플러그인을 경고합니다. 코드의 표(internal/compat/compat.go)와 공개 문서(docs/09-compatibility.md)가 어긋나면 테스트가 실패하도록 묶여 있습니다.

> **현재 "검증됨"은 4개뿐입니다.** HTTP·액세스 로그·애플리케이션 로그 프로브와 webhook 실행기이며, 근거는 CI에서 실제 프로세스로 돌리는 E2E 데모입니다. 상용 장비(F5, vCenter, Nutanix, AWS, OpenStack 등)와 연동한 검증은 아직 한 건도 없습니다.

## 5.6 지원하지 않는 영역

- Azure Load Balancer·Application Gateway, Citrix ADC: 전용 트래픽 제어기가 없어 `exec`·`webhook`으로 우회해야 합니다.
- EC2·Azure VM: SSH 기반 수집과 symlink·container·exec 실행기의 대상으로 쓸 수 있지만, 클라우드 전용 스냅샷 실행기는 없습니다. AWS는 ALB 트래픽 제어만 지원합니다.
- AIX·Solaris·HP-UX: `host` 프로브는 Linux `/proc` 전용이라, 이 OS들은 `exec` 기반 프로브 추가가 필요합니다.
- neutron-lbaas(OpenStack 레거시 LB): 지원하지 않으며 `exec`로 우회합니다.

## 6.2 고가용성

여러 서버 노드가 PostgreSQL을 공유하고, DB의 리더 리스로 하나의 리더만 판정·롤백을 실행합니다. 리더 자리를 잃은 노드의 기록은 DB가 거부하므로(펜싱) 두 노드가 동시에 결정을 남기지 않고, 새 리더는 진행 중이던 롤백을 이어서 끝냅니다. 팔로워는 받은 요청을 리더로 전달합니다(docs/02 "server", docs/01 5장).

> **참고:** 비기능 목표(가용성 99.9%, 리더 장애 시 30초 안에 인계)는 로드맵의 제안값이며 측정하지 않았습니다.

**부하·장애 시험 (M5-4, PR #12로 master에 병합):** GitHub Actions(ubuntu-latest)에서 엔진 하나가 HTTP 시뮬레이터 대상을 관측하고 동시 배포 중 일부를 불량으로 만들어 측정했습니다(test/load, .github/workflows/load.yml).

| 규모 | 오판 | 판정 지연 p99 (목표 12초) | 프로브 요청/초 | 최대 힙 | 평균 CPU |
|---|---|---|---|---|---|
| 대상 2,000 × 프로브 3, 동시 배포 100 | 0 | 5.5초 | 2,804 | 352 MiB | 0.45코어 |
| 대상 2,000 × 프로브 10, 동시 배포 100 | 0 | 5.7초 | 9,095 | 1.1 GiB | 0.72코어 |

- 대상은 SSH가 아닌 HTTP 시뮬레이터이므로 sshd 부하는 재지 않았습니다.
- 부하 시험은 주 1회와 엔진을 바꾸는 PR마다 다시 돕니다. 관측 장치 보호를 넣은 PR #13의 CI에서도 두 규모 모두 오판 0건이었고, 프로브 10개 규모는 판정 지연 p99 6.0초, 최대 힙 약 1.05 GiB, 평균 1.24코어였습니다(프로브 3개 규모는 p99 5.3초, 388 MiB, 0.34코어). CPU 사용량은 러너에 따라 달라지므로 위 표의 CPU 값은 참고로만 봅니다.
- 장애 주입 시험: 롤백 중·롤백 시작 시점의 상태 저장소 단절, 저장소 장애 시 롤백 거부 모드(`on_unavailable: fail`), LB API 일시 오류·지연, LB 완전 장애, 관측 장치 과부하(internal/orchestrator/chaos_test.go).
- **상태 저장소 장애의 한계:** 쓰지 못한 기록을 담는 대기열은 메모리에만 있어 장애 중 프로세스가 죽으면 그 몫을 잃고, 10만 건을 넘으면 버립니다. HA에서 저장소 장애가 리더 리스 시간(`lease_ttl`)보다 길면 리더가 물러나 판정이 멈추고, 다른 노드가 리더가 되면 대기열은 버려집니다. 장애 중 서비스 잠금 없이 진행한 롤백은 다른 프로세스의 롤백과 겹칠 수 있으며, 저장소가 돌아왔을 때 겹침이 확인되면 `lease.conflict`로 알립니다.
- **관측 장치 과부하:** 다른 작업으로 바쁜 개발 PC에서 같은 시험을 돌리자 관측 쪽 과부하로 생긴 프로브 시간 초과를 대상 장애로 판정해 정상 배포 90건을 롤백한 일이 있었습니다. 그 대책으로 관측 장치 보호(`safety.observer_guard`, 3.3절)를 넣었고, 과부하 신호를 주입한 시험으로 보류되는 것을 확인했습니다. 다만 같은 과부하 PC 조건에서 다시 측정하지는 않았고, 보호가 작동하는 동안에는 실제 불량 배포도 서버가 직접 재는 프로브의 실패 지표만으로는 롤백되지 않고 보류됩니다(액세스 로그·로그·컨테이너 지표는 그대로 판정). 서버 자원은 위 측정값(프로브 2만 개에 힙 약 1.1 GiB)보다 넉넉히 잡고 `vigilante_observer_degraded` 지표를 감시하십시오.

| 컨테이너 이미지 | distroless, non-root, 멀티 아키텍처 |
| Helm 차트 | 단일 노드(파일 저장소) 또는 HA(PostgreSQL). 인증 설정이 없으면 렌더링을 거부(개발용 `auth.allowAnonymous`만 예외), 서버 TLS를 켜면 HA 전달·프로브·Ingress·ServiceMonitor를 https로 구성, 메모리 기본 요청 512Mi·한도 2Gi |
| 폐쇄망 번들 | 위 산출물과 SBOM·문서·설치 스크립트를 아키텍처별로 묶음 |
| SBOM | 바이너리별 CycloneDX |
| 체크섬·서명 | 모든 파일의 `SHA256SUMS`와 cosign 서명 (릴리스 키는 아직 생성 전) |

| 분류 | 대상 | 내용 | 현재 시험 방식 |
|---|---|---|---|

# 9. 현재 한계와 도입 검토 시 유의 사항

## 9.1 알려진 한계

1. **실장비 검증 없음:** F5, AWS, Nutanix, vCenter, OpenStack 실제 환경과는 연동 테스트를 하지 않았습니다. 특히 Nutanix는 Prism Element v2 API 경로 기준이라 AOS 버전별 확인이 필요하고, OpenStack Cinder의 `revert_to_snapshot`은 스토리지 백엔드에 따라 사용 중 볼륨을 거부할 수 있습니다.
2. **판정 품질 미측정:** 오탐(정상 배포를 롤백)과 미탐(장애 배포를 통과) 비율을 실제 서비스에서 잰 적이 없습니다.
3. **대상 호스트 sudo 기본값:** `connection.sudo`를 켜고 `sudo_scope`를 지정하지 않으면(기본값 `all`) 모든 명령을 `sudo -n sh -c`로 실행하므로 사실상 root 권한이 필요합니다. `sudo_scope: changes`와 `vigilante sudoers`로 바꾸는 명령만 허용하도록 설정해야 합니다(`validate`·`doctor`가 경고).
4. **인증 미설정 시 익명 관리자:** `auth`를 설정하지 않으면 모든 API 호출이 익명 admin입니다. 패키지 기본 설정은 그래서 `127.0.0.1`에서만 받고, Helm 차트는 인증 설정이 없으면 설치를 거부합니다(개발용 `auth.allowAnonymous: true` 예외, `existingConfigMap`은 확인하지 못함). 서버 자체는 경고만 남기므로 바이너리·이미지를 직접 실행할 때는 `auth`를 먼저 설정해야 합니다.
5. **Windows 서비스 미지원:** Windows 바이너리는 CLI·CI 용도입니다.
6. **에이전트 인증서 자동 발급 없음:** 에이전트 mTLS 인증서는 사내 CA나 cert-manager로 발급해 파일로 넣어야 합니다.
7. **부하 시험은 시뮬레이터 기준:** 대상 2,000대·동시 배포 100건 규모 측정(6.2절)은 HTTP 시뮬레이터 기준이라 SSH 부하는 재지 않았습니다. 관측 장치 과부하를 대상 장애로 오판하던 문제는 관측 장치 보호로 막았지만, 실제 과부하 조건에서 다시 측정하지는 않았습니다.
8. **상태 저장소 장애 대기열은 메모리에만 있음:** 저장소 장애 중 프로세스가 죽으면 그동안의 기록(감사 기록 포함)을 잃을 수 있고, 10만 건을 넘는 기록은 버립니다.
9. **외부 보안 점검 미실시:** 외부 침투 테스트와 보안 인증은 없습니다.
10. **릴리스 서명 키·패키지 메타데이터 미확정:** 릴리스 서명 키가 없고(`packaging/cosign.pub` 없음), 패키지의 maintainer·license 값은 임시값입니다(packaging/nfpm.yaml).

## 9.2 권장 도입 방식

로드맵의 파일럿 절차(docs/11-pilot.md)를 그대로 도입 검토 절차로 쓸 수 있습니다.

1. **사전 점검:** `vigilante validate`와 `vigilante doctor`로 설정, 접속, sudo 규칙, 로그 형식, 이전 릴리스, LB 풀, 자격증명을 읽기 전용으로 확인합니다.
2. **1개월차 드라이런:** `server.dry_run: true`로 판정만 하고 조치는 로그로 남겨, 판정이 맞는지 평가(`vigilante feedback`)합니다.
3. **2~3개월차 승인 모드:** `rollback.mode: approve`로 실제 롤백을 사람이 승인한 뒤 실행합니다.
4. **판정 품질 보고서:** `vigilante pilot report`로 오탐·미탐·보류 비율과 롤백 시간을 확인하고, 기준을 충족한 서비스만 자동 모드로 전환합니다.
