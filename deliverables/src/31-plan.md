# 1. 개요

본 문서는 Vigilante 제품화 계획(1.0, 2026-10-10)을 그 뒤의 개발 진행 결과에 맞춰 갱신한 기획서이다. 기준 시점은 2026-10-11이며, 진행 현황은 저장소 master 브랜치(병합 커밋 `537870c`, PR #14까지)를 기준으로 한다. 상세 계획과 구현 결과의 원본은 `docs/05-roadmap.md`이다.

## 1.1 배경과 문제

1단계 프로토타입(커밋 `d1e6411`)은 단일 노드에서 핵심 흐름(수집 → 판정 → 롤백 → 안전장치)이 동작함을 증명하였다. 그러나 대규모 조직의 운영 시스템으로 쓰기에는 다음 영역이 부족하였다.

| 영역 | 1단계 시점의 한계 |
|---|---|
| 가용성 | 상태가 단일 노드의 JSONL 파일이며, 오케스트레이터가 중단되면 판정과 롤백도 멈춤 |
| 보안 | 단일 Bearer 토큰, 비밀값은 환경변수, 에이전트 통신이 평문 HTTP일 수 있음 |
| 감사·통제 | 작업자 식별·변조 방지·변경 승인·동결 기간 연동 없음 |
| 사용성 | 서비스당 약 80줄 YAML, 배포마다 수동 인자, 권한 문제가 롤백 시점에야 드러남, 규칙이 없으면 무조건 PASS |
| 규모 | 한 프로세스가 모든 대상을 수집, SSH 동시 세션 한도(기본 10), 연결 단위 sudo, DB 프로브의 커넥션 생성 부담 |
| 신뢰 | 실제 F5·vCenter·Nutanix·AWS 장비 검증 없음, 패키징·서명·업그레이드 절차 없음 |
| 판정 품질 | 실제 서비스에서 오탐·미탐 비율을 측정한 적 없음, 프리셋 임계치는 추정값 |
| 플랫폼 | 사내 CMP의 주력 프라이빗 클라우드인 OpenStack(Nova·Cinder 스냅샷, Octavia LB) 미지원 |
| 도입 장벽 | 운영 환경 자동 롤백을 금융·공공의 변경관리가 허용할지 불확실, 사람 승인 모드와 ITSM 연동 없이는 도입 심사 통과가 어려움 |

## 1.2 목표

수천 대 규모의 하이브리드 환경에서 **고가용성으로 동작하고, 사내 인증·비밀관리·변경관리 체계에 연결되며, 모든 결정과 조치가 감사 가능하고, 관리자가 적은 입력으로 안전하게 운영할 수 있는 제품**으로 만든다.

## 1.3 제품 정의

Vigilante는 이기종 하이브리드 인프라(베어메탈, OpenStack·vSphere·Nutanix·KVM, EC2·Azure VM, Docker·Podman, Nginx·HAProxy·Envoy·F5·ALB·Octavia)의 배포를 **외부 APM 없이 자체 측정·판정하고, 실패 시 롤백**하는 단일 Go 바이너리이다.

- 수집: HTTP·gRPC·TCP 프로브, `/proc`, Docker 소켓, 로그, 액세스 로그(5xx), DB 풀.
- 판정: 복합 규칙, 베이스라인, 연속 실패, 대조군, 관측 쿼럼(PASS·FAIL·HOLD 3값).
- 롤백: 트래픽 드레인 → symlink·컨테이너·스냅샷 복원 → 검증 → 트래픽 복귀.
- 안전장치: 서킷 브레이커, blast radius 제한, 플래핑 제한, 크래시 후 재개.
- 운영 형태: CI 게이트(단발 실행), 중앙 서버(HA), 서버 + CLI 위임, 선택형 에이전트.

## 1.4 범위(1차·2차)

상용 1차는 "파일럿 고객 1곳에서 실제 롤백 성공 사례를 만드는 데 필요한 최소 범위"로 정한다. 그 이후의 확장(M2 거버넌스, M3-4~6 API 확장, M5 규모)은 고객 수요로 순서를 정한다.

| 영역 | 1차 범위 | 1차에서 제외(2차) |
|---|---|---|
| 운영 형태 | CI 게이트(단발), 중앙 서버 + HA, 서버 + CLI 위임 | 에이전트 대규모 관리(M5-2), 수집 샤딩(M5-1) |
| 실행기 | `symlink`, `container`, `openstack`(M7), `exec`, `webhook`. vSphere·Nutanix·KVM은 M8 실장비 검증 통과분만 정식, 나머지는 "실험적" | — |
| 트래픽 제어 | `nginx`, `haproxy`, `f5`, `octavia`(M7). `envoy`·`aws_alb`는 M8 검증 결과에 따름 | Azure LB·App Gateway, Citrix ADC |
| 입력·점검 | 프리셋, 입력 자동 채우기, doctor(M1) | init·discover·inventory·suggest(M2-3) |
| API | v2 핵심(M3-1~M3-3): 명세, 인증·스코프·호출 한도, 이벤트 웹훅·SSE | 확장 API, SDK 4종, 개발자 포털, 샌드박스(M3-4~M3-6) |
| 콘솔·통제 | 웹 콘솔, 승인 워크플로우, 변경 동결, 승인 모드, ITSM 1종(ServiceNow)·알림 | 콘솔 설정 편집(GitOps PR 생성, M2-2 선행), ITSM 추가 연동 |
| 신뢰 | 실장비 호환성 매트릭스, 파일럿 판정 품질 보고서, race detector CI(M8) | 부하·카오스 테스트(M5-4. 2차로 분류했으나 PR #12로 먼저 완료) |
| 출시 | 패키징·서명·SBOM, 업그레이드, 문서·support-bundle(M6) | — |

# 2. 시장·상용화 관점

## 2.1 상용화 검토(2026-10-10)

기획서와 코드를 상용화 관점에서 검토한 결과를 로드맵에 반영하였다(PR #5, 병합 커밋 `1765f96`). 요지는 다음과 같다.

1. VM·베어메탈용 메트릭 기반 자동 롤백은 경쟁 공백이 실재하며, 국내 금융·공공·통신의 폐쇄망 레거시 환경과 맞는다.
2. 그러나 실장비 검증이 0건이고 판정 품질 데이터가 없어, 기능 추가보다 **현장 신뢰 확보**가 상용화의 병목이다.
3. 사내 CMP의 주력 플랫폼인 OpenStack이 미지원이므로 출시 필수 범위에 넣는다(M7).
4. 고객이 생기기 전의 SDK 4종·개발자 포털·샌드박스는 과잉 투자이므로 뒤로 미루고, 영업과 구매 심사에 필요한 웹 콘솔과 승인 워크플로우를 앞당긴다(M4).
5. 운영 초기 기본 모드는 "자동 판정 + 사람 승인"으로 시작한다.
6. 일정 추정은 실측이 아니므로 실장비 랩과 파일럿을 포함해 1.5~2배를 본다.

마일스톤 번호는 식별자로 유지하고, 실행 순서와 범위만 바꾸었다.

## 2.2 상용화 관점의 시사점

- **구매 심사 대응:** 국내 엔터프라이즈 구매 심사는 UI 시연을 요구하므로 웹 콘솔을 1차에 포함하였다. 다만 콘솔의 데모 재생 모드는 1차 구현에서 제외되었다(4.6절).
- **도입 심사 대응:** 승인 모드, 변경 동결, ServiceNow 변경 티켓 게이트, 감사 기록(해시 체인)이 금융·공공 변경관리 심사의 전제 조건이다. 1차 범위에 모두 구현하였다.
- **영업 근거:** 파일럿의 판정 품질 보고서가 영업 자료의 근거가 된다. 현재 보고서 생성 도구(`vigilante pilot report`)는 준비되었으나 파일럿 데이터는 없다.
- **확인되지 않은 사항:** 저장소 문서에는 시장 규모, 가격, 경쟁 제품 비교, 특정 고객사 정보가 기록되어 있지 않다. 본 문서도 이를 다루지 않는다.

# 3. 설계 원칙과 비기능 목표

## 3.1 설계 원칙

1. **롤백 경로는 의존성이 가장 적어야 한다.** 웹 콘솔, ITSM, SSO, Vault 같은 외부 연동이 장애여도 판정과 롤백은 계속 동작한다. 외부 연동 실패는 HOLD나 알림으로 처리하고 롤백을 막지 않는다. 예외는 명시적으로 승인 게이트를 설정한 경우이다.
2. **플러그형 백엔드.** 상태 저장소, 인증, 비밀관리, ITSM, 알림은 인터페이스로 두고 개발용 기본 구현(file, 토큰, env)을 유지한다. 단일 바이너리 데모는 계속 동작해야 한다.
3. **선언형 설정을 코드로 관리(GitOps).** 설정의 원본은 Git이고, UI 편집은 PR 생성 또는 검증된 기록으로 남긴다.
4. **기존 1단계 인터페이스는 하위 호환을 유지한다.** CLI 종료 코드, REST v1, 설정 v1은 변경 시 v2를 신설하고 마이그레이션 도구를 제공한다.
5. **실장비에서 검증하지 않은 실행기·트래픽 제어기는 출시 범위에 넣지 않는다.** 시뮬레이터·mock만 통과한 플러그인은 "실험적"으로 표시하고 `validate`가 경고한다.
6. **운영 초기 기본 모드는 "자동 판정 + 사람 승인"이다.** 판정과 롤백 계획은 자동으로 만들되 실행은 승인 뒤에 한다. 파일럿 데이터로 오탐이 충분히 낮다고 확인된 서비스부터 완전 자동으로 전환한다(서비스 단위 설정). 원칙 4와의 충돌은 8.1절의 결정으로 해소하였다.

## 3.2 비기능 목표(제안값, 확정 필요)

| 항목 | 목표 | 현재 상태 |
|---|---|---|
| 규모 | 클러스터당 대상 2,000대, 동시 관측 배포 100건, 대상당 프로브 10개 | 부하 하네스(PR #12, GitHub Actions ubuntu-latest, 단일 엔진·HTTP 시뮬레이터)에서 대상 2,000 × 프로브 10, 동시 배포 100 기준 오판 0, 9,095 요청/초, 최대 힙 1.1 GiB, 0.72코어. 실제 SSH 대상 부하는 미측정. Helm 기본 메모리는 이 결과에 맞춰 요청 512Mi·한도 2Gi로 올림(PR #13) |
| 판정 지연 | 위반 발생부터 롤백 시작까지 `eval_interval × for + 5초` 이내 | 지표(`vigilante_rollback_trigger_seconds`, `vigilante_evaluation_seconds`) 구현. 부하 하네스에서 p99 5.5초(프로브 3개)·5.7초(프로브 10개), 목표 12초. 실서비스 측정 없음 |

| 감사 | 모든 결정·조치에 작업자와 근거 기록, 변조 검출, 보존 기간 설정(기본 1년) | 해시 체인·`audit verify`·SIEM 내보내기 구현. 체인 키(HMAC, `audit.chain_key_ref`)와 SIEM TLS 전송(`tls://`) 추가(PR #13). 체인 키 교체는 미지원 |
| 보안 | 내부 통신 TLS 1.2 이상(에이전트 mTLS), 비밀값 디스크 평문 저장 금지, 최소 권한 | 서버 HTTPS·에이전트 클라이언트 인증서·Vault 참조 구현. PR #13에서 HA 노드 간 TLS 검증(`server.ha.tls`), 권한이 큰 로컬 CLI 명령 제한(`auth.local_cli`, `--break-glass`), Helm 인증 필수화, 콘솔 HSTS 추가. sudo 최소 권한은 선택 설정(7절) |
| 판정 품질 | 파일럿 3개월·배포 30건 이상에서 오탐 0건, 미탐 0건, HOLD 비율 10% 이하 | 미측정(파일럿 미착수) |

> 위 목표값은 로드맵에 "제안값, 확정 필요"로 기록되어 있으며, 아직 확정 결정이 없다.

M5는 2차로 분류되어 있으나 M5-3과 M5-4는 먼저 완료되었다. M6-4 보안 가이드 작성 중 `connection.sudo: true`가 사실상 root 권한을 요구한다는 한계가 확인되었고, 로드맵은 그 근본 해결을 M5-3으로 지정하였다. M5-4는 저장소 단절 시 기록 유실 위험을 줄이므로 2차 분류와 관계없이 병합하였다(PR #12).

의존 관계는 다음과 같다.

- M0(상태 저장소·인증)이 M3·M4·M5의 선행이다.
- M3 핵심(M3-1~M3-3)이 M4 콘솔과 CLI 원격 모드의 선행이다(API-first).
- M7 OpenStack이 M8 랩·파일럿의 선행이다.
- M8 파일럿 결과가 M6 출시 게이트의 선행이다.
- M1 프리셋이 M2 init·discover·suggest의 선행이다.
- M2 설정 분리가 M4 콘솔의 설정 편집(GitOps PR 생성)의 선행이다.

## 4.11 검토 결함 수정(PR #13, #14) — 완료

- **배경:** 산출물 검토에서 나온 결함을 마일스톤과 별도로 수정하였다. PR #13, 병합 `dd9a055`. 관측 장치 과부하 판별의 보류 대상을 고친 후속 수정은 PR #14, 병합 `537870c`. 내용은 CHANGELOG `[Unreleased]`의 "Fixed (store·security·integration·deployment·decisions)" 항목과 docs/02·04·07·08·10에 반영되어 있다.
- **판정(관측 장치 과부하):** `safety.observer_guard`(기본 켬)가 서버 자신의 측정이 믿을 수 없는 상태(내부 타이머 지연 1초 초과, 루프백 왕복 1초 초과, 3개 이상 서비스에 걸친 관측 대상 50% 이상의 프로브 시간 초과)를 감지하면, 서버가 직접 재는 프로브(`http`, `tcp`, `grpc`, `db`, SSH로 읽는 `host`)의 실패 지표(`up`, `latency_ms`, `consecutive_failures`, `consecutive_timeouts`, `timeout`)와 모든 프로브의 `probe_error`에 기반한 위반을 롤백 대신 HOLD한다. 회복 후 1분(`grace`)까지 유지하며, 로그·액세스 로그·컨테이너 프로브의 지표(액세스 로그의 `latency_ms` 포함)와 호스트 자원 지표 위반은 그대로 판정한다. 처음 구현(PR #13)은 프로브와 관계없이 지표 이름만 보아 액세스 로그의 `latency_ms`도 HOLD했으나, PR #14(병합 `537870c`)에서 프로브 유형으로 구분하도록 고쳤다(설정 키 변경 없음). 지표 `vigilante_observer_degraded`, `vigilante_observer_degradations_total{signal}`, `vigilante_observer_holds_total`. docs/04 시나리오 S14a.
- **저장소(롤백 시작 시점 장애):** 롤백을 시작할 때 저장소에 닿지 않으면 서비스 lease를 `safety.rollback_lease.wait`(10초) 동안 다시 시도한 뒤, 기본(`on_unavailable: proceed`)은 프로세스 안 잠금만으로 롤백하고 배포 이벤트(`safety`)·감사(`lease.unavailable`)·경고 알림을 남긴다. 저장소가 돌아왔을 때 다른 프로세스가 lease를 잡고 있으면 `lease.conflict`로 알린다. `fail`은 이전 동작(ROLLBACK_FAILED)이다. docs/04 시나리오 S12a.
- **보안:** 인증이 설정된 환경에서 `--server` 없는 로컬 CLI의 승인·거절, 에스컬레이션 승인, `circuit reset|trip`, 동결 중 `--freeze-override`는 `--break-glass "이유"`가 있어야 실행되고(`auth.local_cli`, 기본 `auto`), break-glass는 감사(`breakglass.<작업>`)와 critical 알림을 남긴다. 로컬 승인·거절에도 `four_eyes`를 적용한다. 감사 체인 키(`audit.chain_key_ref`, HMAC-SHA256)와 `audit verify --key`, SIEM TLS 전송(`audit.syslog.address: tls://`, RFC 5425, `audit.syslog.tls`), 콘솔 HSTS를 추가하였다.
- **배포(Helm·HA):** 차트가 인증 설정 없는 `config`의 렌더링을 거부한다(개발용 `auth.allowAnonymous=true`). 서버 TLS를 쓰면 HA 알림 주소·프로브·포트 이름·Ingress 백엔드 포트·ServiceMonitor가 https를 쓰고(`tls.enabled`, `tls.secretName`, `serviceMonitor.tlsConfig`), `server.tls.client_auth: require`는 거부한다. 팔로워가 리더 인증서를 지정한 이름으로 검증하는 `server.ha.tls`(`ca_file`, `server_name`)를 추가하였다. 메모리 기본값을 요청 512Mi·한도 2Gi로 올리고 `GOMEMLIMIT`을 한도의 90%로 넣는다.
- **연동:** `vigilante watch --server`가 `--ticket`·`--freeze-override`를 서버로 보내고 게이트 거부를 종료 코드 3으로 끝낸다(이전에는 전달하지 않고 1). `POST /v1/deployments`가 `change_ticket`·`freeze_override`를 받고 거부 응답에 `code`를 준다. ServiceNow 호출은 일시 오류(접속 오류, 429, 5xx)에 1초·2초·4초 뒤 재시도하고, 인시던트는 백그라운드로 만든다(`vigilante_itsm_calls_total{result="retry"}`).
- **남은 한계:** 4.11의 수정과 관계없이 콘솔 유휴 세션 만료 없음, SMTP STARTTLS의 기회적 사용, `sudo_scope` 기본값 `all`, 릴리스 서명 키 미생성(`packaging/cosign.pub` 없음), 실장비 검증·파일럿 미착수는 그대로이다(7절).

| sudo 기본값 `all` | `sudo_scope`를 두지 않으면 모든 명령을 `sudo sh -c`로 실행하여 사실상 root 권한이 필요하다 | `sudo_scope: changes`와 `vigilante sudoers` 사용 권고, `validate`·doctor 경고 |
| 자동 롤백 기본값 | 하위 호환을 위해 `rollback.mode` 미지정은 `auto`로 해석한다. 원칙 6(승인 모드 기본)과 다르다 | `validate`가 명시를 경고, 파일럿·신규 서비스는 `approve` 명시 |
| 도입 심사 | 운영 환경 자동 롤백을 변경관리가 허용할지 불확실하다. 콘솔 데모 재생 모드는 1차에서 제외되었다 | 승인 모드·변경 동결·ServiceNow 게이트·감사 기록 제공, 데모는 E2E 데모 시나리오로 대체 여부 검토 필요 |
| 상태 저장소 단절 시 기록 유실 | 저장소 기록 실패(펜싱 제외)는 PR #12부터 메모리 대기열에 쌓였다가 복구 후 기록된다. 대기열은 메모리 전용이라 장애 중 크래시, 대기열 상한(100,000건) 초과, HA의 장기 장애 후 리더 교체 시에는 여전히 유실된다 | `vigilante_store_pending_writes`·`vigilante_store_errors_total{reason="dropped"}` 감시, 장애 중 서버 재시작 금지(런북) |
| 저장소 장애 중 lease 없는 롤백 | PR #13부터 롤백 시작 시 저장소에 닿지 않으면 10초 뒤 프로세스 안 잠금만으로 롤백한다. 그 사이 다른 프로세스(다른 CI 잡, 서버)가 같은 서비스에 조치할 수 있다 | `lease.unavailable`·`lease.conflict` 경고 알림 확인 후 대상 점검(런북), 엄격한 환경은 `safety.rollback_lease.on_unavailable: fail` |
| HA 전환 중 단계 중복 | 리더 자리를 잃는 순간 대상에 보낸 명령은 되돌리지 못하므로 새 리더가 같은 단계를 다시 실행할 수 있다 | 모든 롤백 단계를 멱등으로 구현 |
| 규모 목표의 실환경 미검증 | 부하 하네스(PR #12)는 단일 엔진·HTTP 시뮬레이터로 대상 2,000 × 프로브 10, 동시 배포 100을 통과했으나 실제 SSH 대상 부하는 재지 않았다 | 1차는 수십 대 규모 파일럿으로 한정, 서버 크기는 부하 결과(힙 약 1.1 GiB) 기준으로 여유 있게 산정 |
| 관측 장치 과부하 오판 | 관측 쪽이 과부하되면 프로브 시간 초과를 대상 장애로 보아 정상 배포를 롤백할 수 있었다(과부하된 Windows 개발 PC에서 정상 배포 90건 롤백). PR #13의 `observer_guard`가 프로브 실패 기반 위반을 HOLD하도록 보완했고 PR #14에서 그 대상을 서버가 직접 재는 프로브로 한정했으나, 기준값의 실환경 적합성은 미확인이고 과부하 중 실제 불량 배포도 롤백 대신 HOLD되어 사람 판단이 필요하다 | `vigilante_observer_degraded` 경보와 런북 절차, 서버 자원 여유 확보(부하 결과 기준) |
| 로컬 CLI의 권한 우회 | `--server` 없는 CLI는 상태 저장소를 직접 다루므로 역할 검사를 받지 않는다. PR #13부터 인증 환경에서는 권한이 큰 명령에 `--break-glass`가 필요하지만, 수동 롤백·`mark-good` 등은 제한되지 않고 저장소 접근 권한 자체가 우회 수단이다 | 저장소 계정(DB 사용자, 저널 파일 권한)을 운영자에게만 부여, `breakglass.*` 감사·critical 알림 검토 |
| 감사 체인 키 운용 | 체인 키(`audit.chain_key_ref`)는 선택 설정이고 키 교체를 지원하지 않는다. 키 없이 운영하면 저장소 쓰기 권한자가 기록을 고치고 체인을 다시 계산할 수 있다 | 운영 환경에 체인 키 설정(Vault), 처음 설정 시점의 `keyed_from`을 외부에 기록, 유출 의심 시에만 교체(docs/10) |
| 보안 점검 잔여 항목 | 콘솔 유휴 세션 만료 없음, SMTP STARTTLS는 메일 서버가 지원을 알릴 때만 사용(보안 점검표 응답서 VGL-BD-02의 AU-07, EN-10) | IdP 토큰 수명 단축, 신뢰 망 안의 메일 릴레이 사용 |
| 출시 절차 미완 | 릴리스 서명 키가 없어 릴리스 워크플로우가 실패하고, 패키지 메타데이터가 임시 값이다 | 릴리스 관리자가 키 생성·등록, 메타데이터 확정 |
| 일정 추정의 불확실성 | 추정은 1인 기준 실측 아님이며, 장비·대상 서비스 확보는 일정에 포함되지 않는다 | 1.5~2배 보정, 파일럿을 가장 먼저 시작 |
| 지원 범위 한계 | `host` 프로브는 Linux 전용, Azure LB·Application Gateway·Citrix ADC는 미지원이다 | `exec`·`webhook`으로 우회, 우선순위는 고객 수요로 결정 |

# 9. 다음 단계

1. **파일럿 대상 서비스 선정과 착수:** 달력상 임계 경로이므로 가장 먼저 시작한다. 1개월차 `dry_run`, 2~3개월차 `rollback.mode: approve`로 운영하고 매주 `vigilante pilot report`로 평가 누락을 채운다.
2. **M8 랩 장비 확보와 실측:** 사내 OpenStack(Octavia)을 우선으로 1차 범위 플러그인에 `vigilante lab run`을 실행하고, 3회 연속 통과 시 `internal/compat`과 docs/09를 함께 "검증됨"으로 갱신한다.
3. **릴리스 준비 마무리:** 릴리스 서명 키 생성·등록, `packaging/cosign.pub` 커밋, 패키지 `maintainer`·`license` 확정. 이후 사전 릴리스 태그로 릴리스 워크플로우를 시험한다.
4. **PR #12·#13·#14 반영 확인:** 기존 Helm 설치는 업그레이드 전에 인증 설정과 메모리 값을 점검하고(docs/08), 파일럿 환경에서 관측 장치 과부하 지표(`vigilante_observer_degraded`)와 저장소 대기열 지표(`vigilante_store_pending_writes`)를 경보에 넣어 동작을 확인한다.
5. **결정 필요 사항 확정:** 비기능 목표, 지원 OpenStack 버전, 파일럿 대상, 키 관리 책임자.
6. **파일럿 결과 반영:** 판정 품질 보고서 확정, 프리셋 v2 보정, 검증되지 않은 플러그인의 1차 범위 제외 여부 결정 후 출시 게이트를 판정한다.
7. **2차 계획 수립:** 1차 출시 후 고객 수요에 따라 M2, M3-4~M3-6, M5의 순서를 다시 정한다.
